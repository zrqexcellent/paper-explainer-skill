# Section 9 & 10 写作指导

本文件指导如何撰写两个"增值 section"：技术突破的设计原理（Section 9）和对 AI 产品构建的启发（Section 10）。这两个 section 是本技能区别于普通论文解读的核心差异点——将技术解读提升为产品思维训练。

---

## Section 9：技术突破的设计原理

**目标**：揭示"这个方案是怎么被想出来的"，而非仅仅说明"这个方案是什么"。

### 写作框架

采用 **"问题 -> 直觉 -> 验证"** 三段式：

#### 第一段：前人的思维定式

- 这个领域之前的主流做法是什么？（用 2-3 句话概括）
- 前人做法的根本假设是什么？
- 这个假设看起来合理，但有什么隐蔽的代价？

#### 第二段：作者的关键洞察

- 作者打破了什么假设？（用一句醒目的话概括）
- 作者的"顿悟时刻"可能是什么？（合理推测，标注为推测）
- 为什么这个洞察在当时不是显而易见的？（当时的认知局限是什么）

#### 第三段：从洞察到方案

- 从关键洞察出发，如何一步步推导出最终方案？
- 方案中有哪些"做减法"的设计决策？（去掉什么比加上什么更重要）
- 方案中最反直觉的部分是什么？作者为什么这么选？

### 写作原则

1. **区分事实与推测**：论文中明确说的标注为"论文原文"，合理推断的标注为"推测"
2. **追溯思维路径**：不要只说结果，要还原推理链条（A 导致 B，B 启发了 C）
3. **强调"做减法"**：很多突破不是加法而是减法——去掉不必要的东西（如 Transformer 去掉 RNN）
4. **联系同时代工作**：同期有哪些相关工作？作者的方案在什么语境下显得特别？
5. **控制篇幅**：3-5 个段落 + 1 个 analogy 通俗理解区块，不要写成论文综述

### 示例结构（Transformer）

```
9. 技术突破的设计原理

【analogy 区块】
想象一栋大楼的电梯系统...

【前人的思维定式】
在 Transformer 之前，所有序列建模都遵循一个隐含假设：
"处理序列必须一步一步来"。RNN 如此，LSTM 如此...

【作者的关键洞察】
Vaswani 团队问了一个在当时看来几乎愚蠢的问题：
"如果完全不要 RNN 呢？只用注意力行不行？"

这个洞察之所以在当时不显而易见，因为...

【从洞察到方案】
从这个直觉出发，推导过程是：
1. 如果不要 RNN，就必须有一种方式让每个位置看到所有其他位置 → 自注意力
2. 但只有一种注意力可能不够 → 多头注意力
3. 自注意力没有位置信息 → 位置编码
4. 如何堆叠 → 残差连接 + LayerNorm
```

## Section 10：对 AI 产品构建的启发

**目标**：从产品经理视角提炼可行动的产品设计洞察。

### 写作框架

采用 **"技术原理 -> 产品类比 -> 行动建议"** 三层递进：

#### 第一层：抽象出通用设计原理

从论文的核心技术中提取 3-5 个**可迁移的设计原则**。格式：

| 技术概念 | 抽象原理 | 一句话解释 |
|---------|---------|-----------|
| 自注意力 | 动态权重分配 | 不是平均对待所有输入，而是根据相关性动态分配"注意力资源" |
| 多头注意力 | 多维度审视 | 同一个问题从多个不同视角审视，每个视角捕捉不同模式 |
| 位置编码 | 信息结构化 | 给无序的信息加上结构标记，让模型理解"先后""远近""层级" |

#### 第二层：产品类比

对每个抽象原理，给出一个**产品设计中的直接类比**：

- 自注意力 → 个性化推荐引擎根据用户当前意图动态调整推荐权重
- 多头注意力 → 产品评审时同时从 UX、性能、商业、技术债四个维度评估
- 残差连接 → 产品迭代中保持核心体验的连续性，即使底层架构重构

#### 第三层：行动建议

给产品经理 2-4 条**可立即执行的行动建议**，格式为：

- **[动词短语]**：具体描述 + 为什么重要

示例：
- **构建上下文维护机制**：就像 Transformer 的自注意力让每个 token 看到全局，产品应让用户在任何页面都能快速获取关键上下文
- **设计多视角评审流程**：借鉴多头注意力，关键决策引入多个不同角色的评审视角

### 写作原则

1. **避免空泛**：每条建议必须是具体的、可操作的，不要写"要重视 AI"这种正确废话
2. **双向映射**：先从技术到产品（技术原理 → 产品类比），再从产品到技术（产品问题 → 技术灵感）
3. **连接 AI Native 方法论**：如果用户有 AI Native 工作方法论（上下文维护、让 AI 提问、批测闭环等），主动关联
4. **诚实标注不确定性**：某些类比可能牵强，直接说"这个类比有一定局限"
5. **控制篇幅**：3-5 个设计原理 + 对应产品类比 + 2-4 条行动建议

### 设计原理挖掘指南

从以下角度思考论文中的技术是否可迁移为产品设计原理：

| 技术特征 | 对应产品思考角度 |
|---------|----------------|
| 注意力/权重 | 资源分配优先级、个性化程度 |
| 多头/多视角 | 评审维度、A/B 测试变体、用户分群 |
| 位置编码 | 信息架构、排序逻辑、上下文感知 |
| 残差连接 | 向后兼容、渐进式重构、不丢失已有能力 |
| 并行化 | 工作流效率、批处理、自动化程度 |
| 做减法 | 功能精简、砍需求、MVP 思维 |
| 归一化 | 标准化流程、统一规范 |
| 缩放定律 | 投资回报、资源规划 |

## 两个 Section 的 HTML 呈现

在 HTML 页面中，这两个 section 应有**视觉差异化**，与前面的技术讲解区分开来：

### Section 9（设计原理）的视觉特征

- 使用不同的卡片背景色（如深紫色渐变 `linear-gradient(135deg, rgba(79,70,229,0.2), rgba(139,92,246,0.1))`）
- 标题带灯泡 emoji 或洞察图标
- "前人定式"部分用灰色/暗色卡片
- "关键洞察"部分用高亮边框卡片（`border-left: 4px solid var(--accent)`）
- "推测"内容用斜体 + 标注 `[推测]`

### Section 10（产品启发）的视觉特征

- 使用暖色调渐变卡片（如 `linear-gradient(135deg, rgba(245,158,11,0.15), rgba(16,185,129,0.1))`）
- 设计原理用表格呈现（技术概念 / 抽象原理 / 一句话解释）
- 产品类比用 analogy 区块（橙色左边框）
- 行动建议用带勾选框的列表样式（`✅ **建议标题**`：描述）
